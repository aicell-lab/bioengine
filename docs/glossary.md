# BioEngine Glossary

The canonical names and definitions for the core entities in BioEngine. Implementation details belong in code and `docs/` — this file is purely a glossary.

## App package

A versioned bundle stored in Hypha that contains everything needed to build a BioEngine application: a `manifest.yaml`, one or more Python deployment classes, and optionally a static frontend and a README. An app package does not run — it is the source of truth from which zero or more **applications** are built (one package can be deployed many times, each producing a distinct running application). Referenced in code and API parameters by `artifact_id` in the form `<workspace>/<package-name>` (e.g. `bioimage-io/cellpose-finetuning`).

## Application

A single running deployment of an app package on a specific worker. Created by calling `deploy_app(artifact_id, application_id, version)` on a worker. Identified by `application_id` — either auto-generated via haikunator (e.g. `wandering-cloud-1234`) or user-supplied for stable addressing (e.g. `model-runner`). One app package can have many concurrent applications on the same worker or across workers, each with a distinct `application_id`.

## Worker

A BioEngine deployment unit: a long-running orchestrator process plus the Ray cluster it uses for compute, presented as a single addressable unit. The cluster does the actual compute work — the orchestrator process manages its lifecycle, exposes the Hypha service, and coordinates applications. Identified within its workspace by `client_id` (stable, e.g. `bioengine-worker-kth-abc123`); registers as a Hypha service at `<workspace>/<client_id>:bioengine-worker`. A worker has two internal parts that may differ in location and lifecycle: the **worker process** (the BioEngine Python process) and the **Ray cluster** (the compute backend). In `single-machine` and `slurm` modes the worker process owns its Ray cluster (1:1 lifecycle). In `external-cluster` mode the worker process connects to a pre-existing Ray cluster — they may run on different machines, in different geographic regions, with independent lifecycles. The `worker.get_status()` payload reflects this split: process-level fields at the top level (e.g. `geo_location`), cluster-level fields nested under `ray_cluster.*` (e.g. `ray_cluster.geo_location`).

## Ray cluster

The compute backend inside a worker. A Ray cluster consists of a **head node** (which runs Ray's scheduling layer and BioEngine's `BioEngineProxyActor`) and zero or more **compute nodes** (the CPU/GPU machines on which applications run their Ray Serve replicas). The relationship between a BioEngine worker and its Ray cluster depends on the **deployment mode**: in `single-machine` and `slurm` modes the worker process creates and owns the Ray cluster; in `external-cluster` mode the worker process connects to a pre-existing Ray cluster (typically KubeRay-managed) and is independent of its lifecycle. Cluster-level status is reported under `ray_cluster.*` in `worker.get_status()`.

**Naming note.** Upstream Ray and BioEngine's SLURM scripts call compute nodes "worker nodes" (e.g. SLURM job name `ray_worker`). To avoid collision with the BioEngine **Worker** glossary term, this codebase's user-facing docs say **compute node** instead. The operational names (`ray_worker` job, KubeRay `workerGroupSpecs`) keep the upstream wording.

## Workspace

A Hypha tenant: a named namespace that groups services, artifacts, and authentication. Every BioEngine entity is scoped to exactly one workspace, fixed at the time of creation. Workers are assigned via the `--workspace` flag; app packages are scoped by their `artifact_id` (`<workspace>/<package-name>`); a worker's per-replica application services live in the same workspace as the worker.

Access requires a Hypha token. Two distinct kinds:

- **User token** — obtained interactively via `await login(...)` (browser OAuth). Identifies the user; the workspace is chosen at connect time (`workspace=...`), not baked into the token. Grants access to every workspace the user is a member of, at whatever permission level (`read` / `read_write` / `admin`) the workspace granted them.
- **Workspace-scoped token** — generated by a workspace admin via `generate_token(workspace=..., permission=..., expires_in=...)`. JWT carries a single `ws:<name>#<perm>` scope and a `wid:<name>` claim. Specifying a different workspace at connect time fails with `Current workspace encoded in the token does not match the specified workspace`. Both tokens in this repo's `.env` (`HYPHA_TOKEN`, `BIOIMAGE_IO_TOKEN`) are of this kind.

BioEngine workers do not currently span workspaces — to make the same compute reachable from two workspaces you run two workers (one per workspace), even if they share the same underlying Ray cluster.

See **Permission model** for the full access-control picture; workspace membership is the broadest of three layers but not the only one.

## Permission model

Access to a BioEngine worker and its apps is granted by **any** of three independent layers — they are not nested, and any single layer alone is sufficient.

1. **Workspace membership.** Holding a Hypha token for the worker's workspace (either a user token where the user is a member, or a workspace-scoped token) grants full access to every operation on the worker and every method of every app within it. This is the broadest layer.
2. **Worker `admin_users`.** A list of user IDs / email addresses passed at worker startup via `--admin-users`. These users can perform every admin operation on the worker (`deploy_app`, `stop_app`, `upload_app`, `delete_app`, `run_code`, etc.) **even without** a token for the worker's workspace. They are also auto-injected into every app's `authorized_users` on deploy, so admins can always call any method of any app on this worker.
3. **App `authorized_users`.** Set per app package in `manifest.yaml`, per-method. Each method's `authorized_users` is either `"*"` (public — anyone, including anonymous) or a list of specific user IDs / emails. This grants method-level access to users who have **neither** workspace membership nor worker-admin status.

Identity for layers 2 and 3 is established by the caller's Hypha token (which carries `user_id` and `user_email`) — anonymous callers can only reach methods with `authorized_users: "*"`.

## Service

A callable RPC endpoint registered in a Hypha workspace. In BioEngine, services are how external callers reach a worker and the applications running on it.

## Service ID

Fully qualified handle for a service. Grammar:

```
<workspace>/<client_id>:<service_id>
```

`<client_id>` is the registering Hypha client (stable while connected); `<service_id>` is the name given at registration.

**Two BioEngine service patterns:**

- **Worker service** — one per worker. ID = `<workspace>/<client_id>:bioengine-worker`. The literal `bioengine-worker` is hardcoded; it exposes the worker's admin API (`get_status`, `deploy_app`, etc.).
- **Application services** — one **ProxyDeployment replica per application** (fixed). ID = `<workspace>/<worker_client_id>-<replica_id>:<application_id>` (plus `<application_id>-rtc` for WebRTC). The `<replica_id>` is appended to the worker's `client_id`. An app's internal deployments may have their own Ray Serve replicas, but only the single ProxyDeployment in front of them yields Hypha services; internal deployments are addressed through Ray Serve handles inside the worker.

**Calling an application.** `get_app_status()` returns a `service_ids` block of shape:

```python
{
    "websocket_service_id": "<workspace>/<worker_client_id>-<replica_id>:<application_id>",
    "webrtc_service_id":    "<workspace>/<worker_client_id>-<replica_id>:<application_id>-rtc",
}
```

- **WebSocket** — `get_service(service_ids["websocket_service_id"])`. No selection mode needed; one concrete client.
- **WebRTC** — `get_rtc_service(hypha_client, service_ids["webrtc_service_id"])`. Same concrete replica; peer-connection handshake addresses it directly.
