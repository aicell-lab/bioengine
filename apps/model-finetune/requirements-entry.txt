# Reads one region of a remote OME-Zarr store instead of downloading the whole
# image (ngff_region.py). ENTRY ONLY, on purpose: the two GPU runtimes pin numpy
# irreconcilably (cellpose 1.26.4 vs micro-sam's python-elf >=2), and the crop is
# read where image references are already resolved, so neither runtime needs it.
#
# `zarr<3` is load-bearing twice over, and a bare `zarr` is what broke it:
#
#  1. zarr 3.x declares `numpy>=2.0`, so it pulls numpy 2.x into this overlay and
#     triggers the ABI break described above. Measured: a bare `zarr` resolved to
#     zarr 3.1.6 + numpy 2.4.6 and the entry deployment went DEPLOY_FAILED; in
#     that env even `import zarr` fails, through the image's cupy -> scipy. The
#     same requirement list with `zarr<3` resolves to zarr 2.18.7 + numcodecs
#     0.15.2 and installs NO numpy at all.
#  2. the store wrapper in ngff_region.py is a MutableMapping, which is the zarr 2
#     store interface. zarr 3 replaced it, so zarr 3 would need a different
#     wrapper than the one the tests exercise.
#
# fsspec + aiohttp + requests are NOT optional here, and `pip install zarr` does
# not bring them. zarr reaches an http(s) store through fsspec's HTTPFileSystem,
# which imports requests and aiohttp at construction; without them every region
# read dies at its first open with ModuleNotFoundError: fsspec, and then with
# ImportError: HTTPFileSystem requires "requests" and "aiohttp". Measured in a
# clean py3.11 venv holding only numpy+zarr, which is exactly what an earlier
# version of this file described.
#
# The lesson in one line: `pip install --dry-run zarr` answers what RESOLVES, not
# what WORKS. Opening a remote store is a capability, and it has to be exercised.
