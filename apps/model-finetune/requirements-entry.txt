# Reads one region of a remote OME-Zarr store instead of downloading the whole
# image (ngff_region.py). ENTRY ONLY, on purpose: the two GPU runtimes pin numpy
# irreconcilably (cellpose 1.26.4 vs micro-sam's python-elf >=2), and the crop is
# read where image references are already resolved, so neither runtime needs it.
#
# THE UPPER BOUND IS ON 3.1.6, NOT ON 3, and the difference matters. The bug this
# pin fixes was caused by exactly one release: of every zarr version checked,
# ONLY 3.1.6 declares `numpy>=2.0`. 3.0.0 and 3.0.8 declare `numpy>=1.25`;
# 3.1.0, 3.1.2, 3.1.3, 3.1.4 and 3.1.5 declare `numpy>=1.26`; 2.18.7 declares
# `numpy>=1.24`. All of those are satisfied by the image's 1.26.4, so all of them
# leave numpy alone. A bare `zarr` resolved to 3.1.6, pulled numpy 2.4.6 into the
# overlay and triggered the ABI break above; `zarr>=3.1,<3.1.6` resolves to
# zarr 3.1.5 + numcodecs 0.16.6 and installs NO numpy at all, measured with
# `pip install --dry-run` in the worker environment itself.
#
# `zarr<3` would ALSO keep numpy, and it is the wrong fix for two reasons:
#  1. zarr 2.18.7 cannot open a `zarr.json` array, so every OME-NGFF v0.5 source
#     would stop working — and it would stop working at READ time, after the
#     broker had already probed and imported it, as an ArrayNotFoundError that
#     names nothing. Staying on zarr 3 keeps v0.5 AND v0.4: zarr 3 reads both
#     zarr_format 2 and zarr_format 3 stores.
#  2. CI installs `zarr==3.1.3` (requirements-datasets.txt, via test-suite.yml),
#     so pinning the entry below 3 would make the suite exercise a different
#     zarr major than production runs. The store wrapper is written against the
#     zarr-3 `Store` interface, and zarr 3 rejects a zarr-2 MutableMapping with
#     `TypeError: Unsupported type for store_like`, so the two majors are not
#     interchangeable and the tests have to run on the one that ships.
zarr>=3.1,<3.1.6
